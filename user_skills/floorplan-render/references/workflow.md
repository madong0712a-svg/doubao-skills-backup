# 标准执行流程

> 本文件是 SKILL.md 第六节的展开。执行中出现分支判断时以本文件为准。
> 3.0 相对 2.0 的三处流程变更：
> ① 第二步增加**可施工性判定**；② 第五步前增加**生成能力探测**；
> ③ 每张图的工序由「生成→质检→归档」改为「生成→质检→**后处理**→归档」。
>
> **4.7.1 同步**：总览图对齐 SKILL.md §六/§十四现行主链路（补 [-1] 上传图安全审核、
> [-0.5] 避坑约束加载、[4.5] 平面俯视图、[5] 合规校验、[6.5] 布局确认闸、[6.6] 出图前预审）；
> 质检口径由「11 维度」更正为**五层 17 项**。

## 总览：一条主链，两个入口

> 步号与 SKILL.md §六/§十四一致（[-1]~[9]）；本文件正文按「第零步~第七步」组织，
> 对应关系：第零步=[0] 能力探测 · 第一步=[1] 完整性判定 · 第二步=[2] 房间识别 ·
> 第三步=[3] 风格解析 · 第四步=[6] 预算播报（其前的 [4.5] 平面图与 [5] 合规校验见 SKILL.md）·
> 第五步=[7] 批量生成 · 第六步=[8] 质检 · 第七步=[9] 交付。

```
入口A（默认）：用户发来户型图 + 参考图/风格 ──────────────────────┐
入口B：用户说"先看计划再生成" ──→ 计划确认模式                    │
                                                                 ↓
[-1]   上传图安全审核（涉隐私/敏感内容的图拒绝进入流程，不识别不总结）
        ↓
[-0.5] 避坑约束加载（取值判定表 + 常驻排除 + 房间追加排除 + 正向强化词）
        ↓
[0]    生成能力探测（先探测再调用，不要凭记忆假设参数名）
        ↓
[1]    完整性判定（只在缺户型图或缺风格时问一轮）
        ↓
[2]    房间自动识别 + 可施工性判定 ──→ 《房间识别清单》（优先级 P0-P3 + 可施工性列）
        ↓
[3]    风格解析 ──→ 《风格迁移卡》
        ↓
[4.5]  平面布局 JSON + 平面俯视图（draw_floorplan.py，十一项自检 FAIL=0；
       提示词布局段引用同一 JSON——两图同源）
        ↓
[5]    合规校验（提示词十二段式生成后、调用生图前逐条过红线）
        ↓
[6]    一句话告知 + 预算播报（预算 >60 积分必须等确认）
        ↓
[6.5]  布局确认闸（templates/layout_confirm.md：待确认项非空或有 ⚠️/❌ 房间
       = 硬闸，停下等确认；全清 = 软闸，注明"无待确认项"继续）
        ↓
[6.6]  出图前预审（make_room_prompts.py --dry-run，不调生图；预检 0 告警才出图）
        ↓
[7]    批量生成（P0→P3 串行，每张：独立目录 → 生成 → 读图质检 → **后处理** → 重命名）
        ↓
[8]    质检不过 → 当场重生成（上限1次）→ 仍不过 → 标记缺口
        ↓
[9]    批次交付校验（平面图在场 / 自检 FAIL=0 / 单位与同源）→ 一次性交付全套
```

## 第零步：生成能力探测（3.0 新增，执行前必做）

按顺序探测，命中即用。**不要跳过，不要凭记忆假设参数名。**

```
1. 检索可用的图像生成工具（image generation / 文生图 / 图生图）
2. 加载其 schema，确认以下参数是否存在：
   - 输入图参数：支持几张？是否支持 image1 / image2 / image3 多图输入？
   - 尺寸参数：size / width / height，接受什么格式？
   - 画质参数：quality 或等价档位
   - 输出目录参数：output_dir
3. 三图输入不可用 → 降级为单图（image1=户型图），
   并在交付中注明"跨图一致性锚点未生效，套图色温可能漂移"
4. 多图输入可用 → 必须按第五节的三图规范传参
5. 无任何图像生成能力 → 走"降级交付"（见 SKILL.md 第十四节），
   严禁假装已经生成图片
```

> ⚠️ **为什么必须探测**：图像生成工具的 schema 会随版本变化。
> 直接假设参数名会导致调用失败或静默忽略关键参数（如 output_dir 不生效 → 并发撞名覆盖）。
> 另一条现实教训：**工具名与路径写死等于自断活路**——不要把可移植性绑死在具体工具上。

## 第一步：完整性判定（澄清决策树）

```
收到图片消息
   │
   ├─ 有户型图（可辨认）？
   │     ├─ 否 ──→ 【提问】"无法辨认房间布局，请上传清晰的户型图或平面图"（终止）
   │     └─ 是 ──→ 有风格来源（参考图 或 明确风格描述）？
   │                 ├─ 否 ──→ 【提问】三选一：现代简约/奶油原木/轻奢，或补参考图（终止，等回复）
   │                 └─ 是 ──→ 进入第二步
   │
   └─ 注：目标空间未指定、用途未说明、图片轻微模糊 → 都不问，直接执行
```

**澄清上限：1 轮。** 同一轮里把所有必要的问题一次性问完，禁止连环追问。

> 用户主动提到**城市/小区名**（如"深圳南山 XX 花园 89㎡"）时，不追问、不确认，
> 直接带入第二步后的**户型库交叉校验**（见 §1.5，选填增强项，不提供也能完整执行）。

### §1.5 户型库交叉校验（4.7 新增，P1-6：选填，不自建库）

**定位**：竞品（酷家乐/贝壳/躺平）靠自建户型库在解析前就给用户"你家户型已收录"的确认感。
我们**不自建库**（数据成本 + 版权风险 + 维护熵），用**公开检索**达到同等交叉校验效果：

| 环节 | 口径 |
|---|---|
| 触发 | 用户提供城市 + 小区名（或楼栋/期数）；**缺省不触发、不追问** |
| 动作 | 联网检索该小区公开户型资料（房产平台公开页/楼盘公示信息），取面积段、房间数、布局描述 |
| 一致 | 置信度提升，交付时注明"布局与公开户型资料一致（检索日期）" |
| 不一致 | **以上传图为准**（用户上传图永远是第一事实源），差异列入《待确认事项》：可能是不同楼栋/期数/户型，请用户核对 |
| 查不到 | 只说"未检索到可对照的公开户型资料，按上传图执行"，**不得**说"查无此小区"或编造型号 |
| 隐私 | 只传检索词（城市+小区名+面积段等公开信息），**不传用户上传图片本身**（红线：本机内容不外传） |
| 存储 | **不建库、不落盘、不累积**：每次现查现用，检索结果不进记忆、不进交付物原始数据 |

**边界**：交叉校验只校验"房间数/面积段/整体布局"量级一致性，不作为尺寸依据；
净尺寸一律以图面标注 + 保守推定为准。公开资料本身可能有误，**冲突时上传图优先**。

## 第二步：房间自动识别 + 可施工性判定（3.0 扩展）

### 识别清单

对户型图逐项识别（全部房间，不只用户提到的）：

1. 房间清单：名称、位置（哪个角/中部）、朝向
2. 每房间：墙体关系、门洞、窗户**类型**（平窗/飘窗/落地窗/无窗）、相邻关系
3. **每房间净尺寸**：从图纸标注读取，**扣除管井后取保守值**
4. 户型整体形状、入口位置、主要采光面、主动线
5. 卖点特征
6. 不确定项

### 可施工性判定（3.0 新增，必做）

拿到净尺寸后，对照 `references/buildability.md` 的最小可装尺寸表逐房间判定：

| 判定 | 条件 | 处理 |
|---|---|---|
| ✅ 可行 | 满足常规布局最小尺寸 | 按常规方案生成，提示词不插可施工性段 |
| ⚠️ 紧张 | 满足下限但不舒适 | **采用保守布局**，提示词插入可施工性硬约束段，交付时标注"需现场复核" |
| ❌ 不可 | 低于下限 | **必须改布局**，插入可施工性硬约束段 + 在排除项点名不可施工项 |

判定结果写进《房间识别清单》，作为质检第 17 项的判定依据。

> **不确定净尺寸时取保守值**（按最小可装尺寸反推），并在交付时标注"该空间尺寸需现场复核"。
> 宁可画保守一点，也不要画出物理上做不出的方案。

### 窗户类型标注（批量出图质量的关键）

| 房间情况 | 清单标注 | 生成时的特殊处理 |
|---|---|---|
| 外墙 + 普通平窗 | 平窗 | 排除项追加"落地窗、阳台门" |
| 外墙 + 飘窗 | 飘窗（保留不拆） | 提示词写明"飘窗台保留不改造" |
| 外墙 + 落地窗/阳台门 | 落地窗/阳台门 | 正常保留 |
| 户型内部、无外墙 | **无窗** | 提示词显式写"该房间无窗户，不得出现落地窗/侧窗" |

### 优先级与数量

| 优先级 | 房间 | 默认张数 |
|---|---|---|
| P0 | 客厅 | 2（主视角 + 第二机位） |
| P1 | 主卧、餐厅 | 各 1 |
| P2 | 次卧、书房、厨房 | 各 1 |
| P3 | 卫生间、阳台、玄关 | 各 1 |

- 默认全量 P0-P3；用户说"先出主要房间"→ 只出 P0-P1
- 达到生成上限 → 报告"已完成 N / 剩余 M"，询问是否继续

### 产出

套用 `templates/room_inventory.md`

## 第三步：风格解析

提取 12 项可迁移属性 + 输出不可迁移清单。
**同时从风格库取该风格的【必须排除】块**（见 `references/prompt_templates.md` §5），
与正向关键词一起构成风格段。多张参考图风格略混杂时：**取主导风格直接执行**，交付时注明。

产出：套用 `templates/style_transfer_card.md`

## 第四步：一句话告知 + 预算播报

```
已识别 N 个房间（客厅、主卧、餐厅…），将按参考图风格生成 M 张效果图，
其中 K 个空间因尺寸限制采用保守布局。预计消耗约 {M×5~10} 积分，正在开始。
```

### 批次规模与预算上限（3.0 新增，硬性）

| 房间总数 | 默认生成 | 处理 |
|---|---|---|
| ≤ 6 间 | 全量 P0-P3 | 直接执行 |
| 7–10 间 | P0-P1 全量 + P2 首轮 | 告知"补齐 P2/P3 约需 M×5~10 积分"后执行 |
| > 10 间 | **只出 P0+P1** | 必须先报预算，其余询问后补齐 |

**强制规则**：单批次预计消耗 **> 60 积分**时，必须先告知预算并**等用户确认**，不得静默消耗。
质检重生成不计入预算上限（属必要成本）。

- 播报是**通知**，不是提问；未超预算则发完立即开始生成
- 若用户此时插话要求调整，响应后再继续
- 计划确认模式（用户主动要求）下改为输出完整《效果图执行计划》并等待

## 第五步：批量生成（工程规范，必须遵守）

### 每张图的固定工序（3.0：五步，比 2.0 多一步后处理）

```
① 取提示词（`make_room_prompts.py --prompt RX` 输出后**逐字复制**，禁止人工转写）
② 独立输出目录（如 outputs/{房间名}/）→ 调用图生图
③ 读取生成的图片 → 逐项质检（17 项）
④ ⭐ 走 scripts/postprocess.py 处理水印与尺寸（3.0 新增）
⑤ 通过 → 重命名为 {房源名}_{房间}_{风格}.png 移入 outputs/
   不通过 → 当场重新生成（上限 1 次）→ 仍不过 → 记为缺口，继续下一张
```

### 第四步后处理的具体做法

```bash
python scripts/postprocess.py <刚生成的图> --detect --stretch
```

按检测结果分三条路：

| 底色类型 | 动作 | 命令 |
|---|---|---|
| 未检出 | **保持原图，不做处理**（不做处理是最优解，避免引入新瑕疵） | — |
| texture 多结构底 | 直接裁切，**不要试修复** | `--crop` |
| gradient 渐变底 | 逐行外推修复 | `--fix` |
| flat 平涂底 | 中值填充修复 | `--fix` |

处理后**必须切回正常视角目视确认无新瑕疵**（数值达标 ≠ 视觉达标），
并在交付报告中记录每张图的处置方式。

详见 `references/postprocess.md`。

### 三图输入（跨图一致性的关键）

| image | 内容 | 作用 |
|---|---|---|
| image1 | **户型图** | 结构基准（缺它模型会虚构门窗） |
| image2 | 参考图 | 风格来源 |
| image3 | 已确认的首张成品图（通常是客厅） | 风格锚点，保证全屋同一套材质色温 |

探测确认不支持三图时降级为单图，并声明锚点未生效（见第零步）。

### 硬性禁令

- **禁止同秒并行调用图片生成**——会产生同名文件互相覆盖；必须逐张串行
- **禁止在无户型图输入的状态下生成**——结构必然漂移
- **禁止"先全生成完再看"**——必须生成一张、质检一张、后处理一张、归档一张
- **禁止跳过生成能力探测直接调用**——参数名会随版本变化
- **禁止未经后处理直接交付**——平台水印是交付事故（P1 教训）

### 生成顺序

P0 客厅（2 张）→ P1 主卧、餐厅 → P2 次卧、书房、厨房 → P3 卫生间、阳台、玄关

客厅首张确认后，将其作为 image3 锚点用于后续所有房间。

## 第六步：逐张质检 + 即时重生成

- 每张图独立出质检结论（**五层 17 项** + 主要问题 + 建议动作），格式见 `references/quality_checklist.md`
- **空间结构错误**（门窗漂移/墙体移位/房间数量变化/无中生有窗户）→ 当场重生成，重写提示词强化对应约束
- **可施工性不通过**（画出超出净尺寸的布局）→ 当场重生成，按 `references/buildability.md` §5 的四步兜底处理
- **水印未清**（第 16 项）→ **不走重生成**，走 `postprocess.py` 本地处理
- 重生成上限 1 次；仍不过 → 标记缺口，交付时如实说明，不阻塞其他房间
- 全部完成后做套图一致性检查（配色/材质/色温/家具语言/拍摄高度/可施工性判定标准）

---

## 第七步：一次性交付

交付顺序（全部放在同一次回复中）：

1. 房间识别清单（摘要：N 房间 / M 张 / 缺口 / K 个保守布局）
2. 全部效果图（present_files 一次性全部呈现，客厅排最前）
3. 逐图质检汇总表（五层 17 项）
4. 套图一致性结论
5. 房源营销文案
6. 后续修改建议
7. 风险提示（不得省略）+ **可施工性提示**（判定为 ⚠️/❌ 的房间逐个说明）

## 效果对比流程（2.0 新增）

### 多风格对比

```
用户："再出一套{新风格}对比"
   ↓
复用房间识别清单 + 户型解析（不重新识别）
   ↓
更换风格迁移卡（新风格关键词库）
   ↓
批量串行生成第二套（同机位、同结构约束）
   ↓
交付：按房间两两并排（风格A | 风格B），各自附质检结论
```

### 修改前后对比

保留修改前稳定底图 → 生成新版 → 并排呈现 + 差异点标注。

### 同房间多机位对比

同房间第二机位（机位库见 `references/prompt_templates.md`），结构材质不变。

## 后续修改流程

| 用户表述 | 归类 | 是否重出图 |
|---|---|---|
| "换个风格""整体换轻奢" | 切换另一套风格（走对比交付） | 是（批量） |
| "颜色再暖一点""换木地板" | 仅改局部材质 | 是（指定房间） |
| "沙发换个方向""加个餐边柜" | 仅改家具布局 | 是（指定房间） |
| "换个角度看" | 仅改视角 | 是 |
| "文案改一下" | 仅改文案 | **否** |
| "所有房间都XXX" | 批量修改 | 是（逐张串行，同指令） |
| "把剩下的也出了" | 批量补齐 | 是（按优先级） |

不满意反馈先归类（空间结构错误 / 风格不对 / 视角不好 / 文案不合适）再针对性处理。

## 拒绝场景（立即终止）

- 要求冒充真实房源实拍
- 上传敏感资料并要求识别/总结无关个人信息
- 要求施工图纸、承重墙判断结论、装修报价
- 要求完整复制受版权保护的设计作品
