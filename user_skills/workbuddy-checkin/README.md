# WorkBuddy 积分自动领取

每天手动点一次签到，顺手还得看猫猫旅行到没到点 —— 两件事都不难，但很容易忘。这个 Skill 把这两件事合成一条命令，也可以挂成定时任务，从此不用管。

## 它解决什么问题

WorkBuddy 桌面端有两个每日福利：

- **每日签到**：连续签到天数越久，单次奖励越高（100–1000 积分）
- **猫猫旅行**：派出猫猫出门，1–4 小时后回来带 5–10 积分

两者的共同点是**都需要在特定时间点回来操作一次**：签到每天只能点一次；旅行要等猫猫回来才能领，领完还得再派出去，否则它就一直待在家里不产出。

手动做，等于每天要记得点两次；忘了就断签、断收益。这个 Skill 把它变成「跑一次脚本」或「挂一个定时任务」，脚本自身幂等，重复跑不会重复领。

## 三个子命令，覆盖所有场景

| 命令 | 做什么 | 有副作用吗 |
| --- | --- | --- |
| `status` | 读签到状态 + 猫猫状态 + 旅行状态 | 无 |
| `checkin` | 只签到 | 有（签到） |
| `travel` | 智能调度：空闲就派出、在途只报到达时间、已到达就领取 | 有（派出/领取） |
| `all` | 签到 + 智能调度，日常就用这个 | 有 |
| `selftest` | 只握手 + 列管道，做健康检查 | 无 |

`travel` 不是「无脑领一次」，而是先查 `travel/status` 再决策：

```
idle      → 派出旅行，返回地点和到达时间
traveling → 不重复派，只告诉你几点回来
arrived   → 领取奖励，返回本次积分
```

这一点很关键：早期版本只会调 `claim`，猫猫一旦空闲就永远没有收益。

## 快速开始

```bash
python scripts/main.py all           # 签到 + 自动派出/领取
python scripts/main.py status        # 只看状态，不动任何东西
python scripts/main.py travel --location 2   # 指定去「商场店铺」
```

依赖只有 `pywin32`（已附 `requirements.txt`）。想自动化就在 WorkBuddy 里建一个定时任务，命令填 `main.py all`，建议 6 小时一次 —— 比旅行时长（1–4h）长，能保证每次跑的时候猫猫已经回来。

## 它是怎么工作的

WorkBuddy 桌面端在本地开了一个 **WBIPC 通道**：Windows 命名管道 + 双向 HMAC 证明。这个 Skill 通过 `wb.request` 这个转发器发 HTTP 请求，**Authorization、X-User-Id、X-Domain 等请求头全部由宿主自动注入**。

换句话说，脚本本身不保存、不读取、不传输任何 token 或 cookie。它只是「借用」当前登录态发一个请求，和你在界面里点签到是同一条链路。

## 安全边界

- 端点文件 `endpoint.json` 只给当前用户读写，ticket 只存在宿主内存里
- 握手时客户端会先校验服务端的 HMAC 证明，失败直接中断（防端点抢占）
- 请求头白名单只放 `content-type` / `accept`，其它一律拒绝
- 全程不落盘任何凭证；日志里也不会出现 token

## 已知限制

- **仅 Windows**：依赖 Windows 命名管道与 `pywin32`，macOS/Linux 需要重写连接层
- **必须有已登录的 WorkBuddy 桌面端在跑**：脚本只是转发器，不是独立客户端
- **`daily_limit_reached` 只限制派出**，不影响领取已到达的奖励
- 旅行地点每次由服务端返回为准，当前是 1 咖啡馆 / 2 商场店铺 / 3 健身房 / 4 古镇客栈

## 常见问题

**跑的时候报 `ReadFile err=2`？** 桌面端没开，或者刚重启过。重启 WorkBuddy 再跑。

**报 `E_NOT_CONNECTED`？** 桌面端没登录，登录一次即可。

**报 `server proof verification failed`？** 可能同时开了多个 WorkBuddy 实例，或 `endpoint.json` 被改过。关掉多余实例、重启桌面端刷新 ticket。

**签到返回「今天已签到」？** 正常，说明逻辑生效了，不是错误。
